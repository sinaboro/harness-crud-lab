# 검증 체크리스트

> AI 가 "다 했습니다"라고 한 뒤, **커밋하기 전에** 사람이 확인하는 목록이다.
> 수업 흐름의 **④ 코드 실행 및 테스트**와 **⑤ 오류 확인 → AI 수정 → 재검증**에 해당한다.
> 하나라도 "아니오"면 커밋하지 않는다. AI 에게 고치게 하거나, 직접 고친 뒤 처음부터 다시 확인한다.

---

## 1단계. 기계가 확인하는 것 (1분)

dev 컨테이너에서 실행한다.

```bash
sh scripts/verify.sh
```

- [ ] 마지막 줄이 `검증 통과: 이제 저장(commit)해도 됩니다.` 이다.
- [ ] 통과한 테스트 개수가 지난번보다 **줄지 않았다.** (줄었다면 테스트가 지워진 것이다)

## 2단계. 무엇이 바뀌었는지 확인 (3분)

```bash
git status
git diff --stat
```

- [ ] 바뀐 파일이 **작업 지시서의 "범위"에 적은 파일뿐**이다.
- [ ] `AGENTS.md`, `opencode.jsonc`, `harness/`, `scripts/verify.sh`, `.githooks/` 는 바뀌지 않았다.
- [ ] `.env` 가 목록에 없다. (`.gitignore` 가 막고 있어야 한다)
- [ ] 뜻 모를 새 파일(임시 파일, 백업 파일)이 생기지 않았다.

## 3단계. 테스트를 사람이 읽는다 (5분)

테스트가 통과했다는 것은 "테스트에 적힌 것"이 맞다는 뜻일 뿐이다. 테스트 자체가 엉터리면 통과는 아무 의미가 없다.

```bash
git diff tests/
```

- [ ] 이번 작업의 요구사항 번호마다 테스트가 있다. (아래 대응표로 확인)
- [ ] 정상 경우뿐 아니라 **실패 경우**(없는 번호 → 404, 잘못된 입력 → 422)도 테스트한다.
- [ ] 기존 테스트에서 **지워진 줄(-)이 없다.** 있다면 왜 지웠는지 AI 에게 묻는다.
- [ ] `assert True` 처럼 항상 통과하는 테스트, `skip` 으로 건너뛰는 테스트가 없다.
- [ ] 테스트가 확인하는 값이 요구사항 명세의 값(상태 코드, 오류 문구)과 같다.

### 요구사항 ↔ 테스트 대응표

| 요구사항 | 확인하는 테스트 (완성본 기준) | 확인 |
|---|---|---|
| R1 만들기 | `test_create_memo`, `test_create_memo_without_content` | [ ] |
| R2 목록 | `test_list_memos_empty`, `test_list_memos_newest_first` | [ ] |
| R3 한 건 보기 | `test_get_memo`, `test_get_memo_not_found` | [ ] |
| R4 고치기 | `test_update_memo`, `test_update_memo_not_found`, `test_update_memo_empty_title` | [ ] |
| R5 지우기 | `test_delete_memo`, `test_delete_memo_not_found` | [ ] |
| R6 입력 규칙 | `test_create_memo_empty_title`, `test_create_memo_title_too_long`, `test_create_memo_content_too_long`, `test_create_memo_blank_title`, `test_title_is_trimmed` | [ ] |
| R7 웹 화면 | `test_index_page` + 브라우저에서 직접 확인 | [ ] |

AI 가 지은 테스트 이름은 이 표와 다를 수 있다. 이름이 아니라 **무엇을 확인하는지**를 본다.

## 4단계. 코드를 사람이 읽는다 (10분)

```bash
git diff app/
```

- [ ] 바뀐 코드를 **위에서 아래로 한 번 다 읽었다.**
- [ ] 모르는 줄이 있으면 AI 에게 물어서 이해했다. (예: "`app/main.py` 의 `RETURNING *` 이 무슨 뜻이야?")
- [ ] SQL 에 값을 넣는 곳이 모두 `%s` 다. f-문자열이나 `+` 로 SQL 을 만들지 않았다.
- [ ] `UPDATE`, `DELETE` 에 `WHERE` 가 있다.
- [ ] 비밀번호, API 키, 접속 주소가 코드에 적혀 있지 않다.
- [ ] 시키지 않은 기능이 들어 있지 않다.
- [ ] 한국어 주석이 있고, 주석의 내용이 코드와 맞다.

## 5단계. 직접 실행해 본다 (5분)

테스트가 못 잡는 것(화면 모양, 실제 DB 에 남는지)을 눈으로 확인한다.

- [ ] 브라우저에서 `http://localhost:8000/docs` 를 열어 이번에 만든 주소를 직접 불러 봤다.
- [ ] (8교시 이후) 서버를 다시 켠 뒤에도 메모가 남아 있다.
- [ ] (10교시 이후) `http://localhost:8000` 화면에서 쓰기·수정·삭제를 해 봤다.

## 6단계. 내 말로 설명한다 (5분)

[`WORKLOG.md`](WORKLOG.md) 에 적는다. 적지 못하면 아직 이해하지 못한 것이다. 4단계로 돌아간다.

- [ ] 이번에 바뀐 내용을 **세 문장**으로 적었다.
- [ ] 새로 알게 된 용어나 문법을 **하나 이상** 적었다.

## 7단계. 저장한다

```bash
git add -A
git commit -m "9교시: 메모 수정·삭제 구현 (R4, R5)"
```

- [ ] 커밋 메시지에 **무엇을 했는지**와 **요구사항 번호**가 들어 있다.
- [ ] `pre-commit` 이 검증을 한 번 더 실행했고, 통과해서 커밋이 만들어졌다.

---

## 검증이 실패했을 때

1. 오류 메시지를 **끝까지** 읽는다. 대부분 마지막 몇 줄에 원인이 있다.
2. 어떤 테스트가, 무엇을 기대했는데, 실제로 무엇이 왔는지 찾는다. (`assert 201 == 422` → 422 를 기대했는데 201 이 왔다)
3. AI 에게 **오류 전체를 붙여서** 전달한다. "안 돼요"라고만 하지 않는다.

   ```text
   sh scripts/verify.sh 가 실패했어. 아래가 출력이야.
   원인을 먼저 설명하고, tests/ 는 건드리지 말고 app/ 을 고쳐 줘.

   (오류 출력 붙여넣기)
   ```

4. AI 가 고치면 **1단계부터 다시** 확인한다.
5. 세 번 고쳐도 안 되면 멈춘다. 작업을 되돌리고(`git restore .`) 지시서를 더 작게 나누어 다시 시킨다.
