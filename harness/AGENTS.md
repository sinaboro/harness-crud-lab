# AGENTS.md — 메모 CRUD 프로젝트 작업 규칙

> 이 문서는 **AI 에이전트가 이 프로젝트에서 일할 때 지켜야 하는 규칙**이다.
> 에이전트는 작업을 시작할 때마다 이 문서를 먼저 읽는다.
> 사람(학습자)은 이 문서를 고칠 수 있지만, 에이전트는 고칠 수 없다.

---

## 1. 프로젝트 소개

- **목표**: 메모를 만들고(Create), 보고(Read), 고치고(Update), 지우는(Delete) 웹 서비스를 만든다.
- **사용자**: 프로그래밍을 처음 배우는 학습자. 학습자가 코드를 **읽고 이해할 수 있어야** 한다.
- **기술**: Python 3.12, FastAPI, PostgreSQL 17, psycopg 3, pytest, 화면은 HTML + 자바스크립트(프레임워크 없음)
- **요구사항**: `harness/REQUIREMENTS.md` 에 번호(R1, R2 ...)로 적혀 있다. 구현의 기준은 항상 이 문서다.

### 폴더 구조

| 경로 | 내용 | 에이전트가 고쳐도 되는가 |
|---|---|---|
| `app/` | 서버 코드 (`main.py`, `db.py`, `schemas.py`, `static/`) | 예 |
| `tests/` | 자동 테스트 | 예 (단, 5절의 테스트 규칙을 지킨다) |
| `harness/` | 요구사항, 작업 지시서, 체크리스트 | **아니오** (읽기만) |
| `scripts/verify.sh` | 검증 스크립트 | **아니오** |
| `AGENTS.md`, `opencode.jsonc`, `.githooks/` | 하네스 설정 | **아니오** |
| `checkpoints/` | 교시별 완성 예시 | **아니오** (읽지도 않는다) |
| `.env` | API 키, 비밀번호 | **아니오** (읽지도 않는다) |

## 2. 도구 — 무엇으로 일하는가

에이전트는 **dev 컨테이너 안의 `/workspace`** 에서 실행된다.

| 하려는 일 | 명령 |
|---|---|
| 전체 검증(코드 검사 + 테스트) | `sh scripts/verify.sh` |
| 테스트만 실행 | `pytest -q` |
| 테스트 하나만 실행 | `pytest -q tests/test_memos.py::test_create_memo` |
| 코드 검사만 실행 | `ruff check app tests scripts` |
| 무엇이 바뀌었는지 보기 | `git status`, `git diff` |
| 실행 중인 서버 불러 보기 | `curl -s http://app:8000/health` |

알아 둘 것:

- 서버는 **app 컨테이너**에서 이미 켜져 있다. `app/` 의 파일을 고치면 저절로 다시 켜진다. 에이전트가 `uvicorn` 을 따로 실행하지 않는다.
- 데이터베이스는 **db 컨테이너**에 있다. 접속 주소는 환경 변수 `DATABASE_URL` 에 들어 있다. 코드에 주소나 비밀번호를 직접 적지 않는다.
- 테스트는 별도의 DB(`memo_test`)에서 돈다. 테스트가 학습자의 진짜 메모(`memo_db`)를 지우는 일이 없어야 한다.
- 컨테이너 안에는 `docker` 명령이 없다. 컨테이너를 켜고 끄는 일은 사람이 한다.

## 3. 권한 — 해도 되는 일과 안 되는 일

이 규칙은 `opencode.jsonc` 의 `permissions` 에도 같은 내용으로 걸려 있다.

**묻지 않고 해도 되는 일**

- `app/`, `tests/` 안의 파일을 읽고, 만들고, 고치기
- 2절 표의 검증·조회 명령 실행

**사람에게 먼저 물어봐야 하는 일**

- 2절 표에 없는 명령 실행
- 새 패키지 추가(`requirements.txt` 수정), `Dockerfile`·`docker-compose.yml` 수정
- 인터넷 검색, 웹 페이지 가져오기
- 작업 지시서에 적히지 않은 파일 고치기

**하면 안 되는 일**

- `git commit`, `git push`, `git reset` — 저장과 올리기는 사람이 검토한 뒤에 직접 한다.
- `.env` 읽기·고치기, API 키나 비밀번호를 코드·로그·답변에 적기
- `harness/`, `AGENTS.md`, `opencode.jsonc`, `scripts/verify.sh`, `.githooks/` 고치기
- `checkpoints/` 읽기 (완성 예시를 베끼지 않는다)
- 파일이나 폴더를 통째로 지우는 명령(`rm -rf` 등)

## 4. 작업 절차 — 어떤 순서로 일하는가

모든 작업은 아래 다섯 단계를 순서대로 밟는다. 단계를 건너뛰지 않는다.

1. **읽기** — 작업 지시서와, 거기 적힌 요구사항 번호(R1 ...)를 `harness/REQUIREMENTS.md` 에서 찾아 읽는다. 고칠 파일의 현재 내용도 읽는다.
2. **계획** — 무엇을, 어느 파일에, 어떤 순서로 할지 5줄 안팎으로 말한다. **사람이 "진행"이라고 답할 때까지 파일을 고치지 않는다.**
3. **구현** — 계획한 범위 안에서만 고친다. 범위 밖에 고칠 것이 보이면 고치지 말고 보고에 적는다.
4. **검증** — `sh scripts/verify.sh` 를 실행한다. 실패하면 원인을 찾아 고치고 다시 실행한다. 세 번 고쳐도 통과하지 못하면 멈추고 상황을 보고한다.
5. **보고** — 7절의 형식으로 보고한다. 커밋은 하지 않는다.

요청이 모호하면 짐작으로 진행하지 않는다. 질문을 한 번에 모아서 묻는다.

## 5. 코드 규칙

**공통**

- 한 번에 한 가지 일만 한다. 지시받지 않은 기능을 덧붙이지 않는다.
- 지금 있는 코드의 방식(이름 짓기, 파일 나누기)을 따른다. 새 파일은 꼭 필요할 때만 만든다.
- 새 패키지를 쓰지 않는다. 필요하다고 판단되면 이유를 말하고 사람에게 묻는다.

**학습자가 읽을 수 있는 코드**

- 모든 파일의 맨 위에 "이 파일이 보여 주는 개념"을 한국어 주석으로 적는다.
- 핵심 줄에는 "왜 이렇게 쓰는지"를 한국어 주석으로 짧게 적는다.
- 짧게 줄인 기교보다 풀어 쓴 코드를 고른다. 한 줄에 여러 일을 넣지 않는다.
- 변수와 함수 이름은 뜻이 드러나는 영어 단어로 쓴다 (`m` 대신 `memo`).

**API**

- 주소, 상태 코드, 오류 문구는 `harness/REQUIREMENTS.md` 에 적힌 그대로 구현한다.
- 요청과 응답의 모양은 `app/schemas.py` 의 Pydantic 클래스로 정한다.

**데이터베이스**

- SQL 에 값을 넣을 때는 반드시 `%s` 자리표시자를 쓴다. 문자열을 이어 붙여 SQL 을 만들지 않는다.
- `UPDATE` 와 `DELETE` 에는 반드시 `WHERE` 를 쓴다.
- DB 를 다루는 코드는 `app/db.py` 와 `app/main.py` 의 해당 함수 안에만 둔다.

**테스트**

- 기능을 만들면 그 기능의 테스트도 함께 만든다. 정상 경우와 실패 경우(없는 번호, 잘못된 입력)를 모두 넣는다.
- 테스트 이름과 주석에 요구사항 번호(R1 ...)가 드러나게 한다.
- **테스트를 통과시키려고 테스트를 지우거나, 느슨하게 고치거나, 건너뛰게 만들지 않는다.** 테스트가 틀렸다고 판단되면 고치지 말고 이유를 보고한다.

**화면(HTML·자바스크립트)**

- 프레임워크와 외부 라이브러리를 쓰지 않는다.
- 사용자가 입력한 글은 `textContent` 로 넣는다. `innerHTML` 로 넣지 않는다.

## 6. 검증 — "다 됐다"의 기준

아래를 **모두** 만족해야 작업이 끝난 것이다.

- [ ] `sh scripts/verify.sh` 가 "검증 통과"로 끝난다. (에이전트가 직접 실행해 확인한다)
- [ ] 작업 지시서의 완료 조건을 하나씩 확인했다.
- [ ] 새로 만든 기능마다 테스트가 있다.
- [ ] 지시받지 않은 파일은 바뀌지 않았다. (`git status` 로 확인한다)
- [ ] 비밀 값이 코드에 들어가지 않았다.

검증을 실행하지 않았거나 실패했는데 "완료했습니다"라고 말하지 않는다. 실패했으면 실패했다고 말한다.

## 7. 보고 형식

작업을 마치면 아래 형식으로 한국어로 보고한다.

```text
[한 일]      무엇을 만들었거나 고쳤는지 2~3줄
[바뀐 파일]  파일 이름과, 파일마다 한 줄 설명
[검증 결과]  sh scripts/verify.sh 의 마지막 줄 (통과한 테스트 수)
[요구사항]   이번 작업이 다룬 요구사항 번호와 그것을 확인하는 테스트 이름
[확인 방법]  사람이 직접 눈으로 확인할 수 있는 방법 (주소, 명령)
[남은 일]    하지 못한 일, 범위 밖이라 손대지 않은 문제, 사람이 결정해야 할 것
```

## 8. 설명 요청을 받았을 때

학습자가 "이 코드를 설명해 줘"라고 하면:

- 파일을 고치지 않는다. 설명만 한다.
- 전문 용어를 쓸 때는 한 줄로 뜻을 덧붙인다.
- "요청이 들어와서 응답이 나갈 때까지" 순서대로 설명한다.
- 설명 끝에 학습자가 스스로 확인해 볼 수 있는 질문을 1~2개 붙인다.
