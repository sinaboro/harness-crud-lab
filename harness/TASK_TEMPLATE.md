# 작업 지시서 틀

> AI 에이전트에게 일을 시킬 때 쓰는 틀이다. 수업 흐름의 **② AI 에이전트에게 개발 지시**에 해당한다.
> "메모 앱 만들어 줘" 한 줄 대신, 아래 여섯 칸을 채워서 건넨다.
> 채운 예시는 [`tasks/`](tasks/) 폴더에 있다.

---

```markdown
# 작업 지시서: (작업 이름)

## 1. 목표
(이 작업이 끝나면 무엇이 되어 있어야 하는지 한두 문장)

## 2. 요구사항
(harness/REQUIREMENTS.md 의 번호. 예: R1, R2, R3)

## 3. 범위
- 고쳐도 되는 파일: (예: app/main.py, app/schemas.py, tests/test_memos.py)
- 고치면 안 되는 것: (예: tests/test_health.py, 이미 통과하는 테스트의 내용)

## 4. 하지 말 것
- (이번 작업에서 만들지 않을 기능. 예: 수정·삭제는 만들지 않는다)
- (쓰지 않을 방법. 예: 새 패키지를 추가하지 않는다)

## 5. 완료 조건
- [ ] sh scripts/verify.sh 가 "검증 통과"로 끝난다
- [ ] (눈으로 확인할 수 있는 조건. 예: POST /memos 를 부르면 201 이 온다)
- [ ] (요구사항마다 테스트가 있다)

## 6. 진행 방법
AGENTS.md 의 작업 절차를 따른다. 먼저 계획을 말하고, 내가 "진행"이라고 하면 구현한다.
끝나면 AGENTS.md 의 보고 형식으로 보고한다.
```

---

## 칸마다 왜 필요한가

| 칸 | 비워 두면 생기는 일 |
|---|---|
| 1. 목표 | AI 가 "무엇이 끝인지" 몰라서 계속 덧붙이거나, 반만 하고 끝낸다. |
| 2. 요구사항 | 주소·상태 코드·오류 문구를 AI 가 제멋대로 정한다. 매번 결과가 달라진다. |
| 3. 범위 | 관계없는 파일까지 고친다. 무엇이 왜 바뀌었는지 사람이 따라갈 수 없다. |
| 4. 하지 말 것 | 시키지 않은 기능(로그인, 검색 ...)이 생긴다. 읽고 검토할 코드가 불어난다. |
| 5. 완료 조건 | "다 했습니다"라는 말을 확인할 방법이 없다. |
| 6. 진행 방법 | 계획 없이 바로 고치기 시작한다. 방향이 틀려도 끝난 뒤에야 알게 된다. |

## 좋은 지시와 나쁜 지시

| 나쁜 지시 | 왜 나쁜가 | 고친 지시 |
|---|---|---|
| "메모 기능 만들어 줘" | 범위도 기준도 없다 | "R1~R3 을 구현해 줘. 저장소는 메모리. 수정·삭제는 만들지 않는다." |
| "에러 나는데 고쳐 줘" | 어떤 오류인지 AI 가 추측해야 한다 | "`sh scripts/verify.sh` 결과를 붙인다. `test_get_memo_not_found` 가 실패한다. 원인을 먼저 설명하고 고쳐 줘." |
| "알아서 잘 해 줘" | 판단을 전부 넘긴다 | "두 가지 방법이 있으면 장단점을 말하고 내 선택을 기다려 줘." |
| "테스트 통과하게 해 줘" | 테스트를 고쳐서 통과시킬 수 있다 | "`app/` 의 코드를 고쳐서 통과시켜 줘. `tests/` 는 고치지 않는다." |

## 한 번에 얼마만큼 시킬 것인가

작업은 **작게** 나눈다. 이 과정에서 CRUD 를 한 번에 시키지 않고 6·8·9·10·11교시로 나눈 이유다.

- 작은 작업은 AI 가 틀릴 여지가 적다.
- 바뀐 코드가 적어서 사람이 **읽고 이해할 수 있다.**
- 문제가 생기면 그 작업만 되돌리면 된다.

기준: **AI 가 바꾼 내용(`git diff`)을 내가 10분 안에 읽고 설명할 수 있는 크기.**
