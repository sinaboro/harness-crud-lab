# 5교시. 하네스 규칙 작성

| | |
|---|---|
| 시간 | 2시간 |
| 실습 결과 | `AGENTS.md` (그리고 권한 설정과 검증 장치) |
| 시작 상태 | 4교시를 마친 상태 (GET·POST `/memos` 가 메모리 저장으로 동작하고 커밋되어 있다) |

막혔거나 4교시 결과가 없으면 **[dev]** `sh scripts/checkpoint.sh 04` 로 4교시 완성 예시를 가져온다.

## 수업의 흐름에서 이번 교시의 위치

```text
 ① 요구사항 작성 → ② AI 에게 지시 → ③ 하네스로 제어 → ④ 실행·테스트 → ⑤ 수정·재검증·저장
                                     └─ 이번 교시: 하네스를 직접 세운다 ─┘
```

이 과정에서 가장 중요한 교시다. 여기서 세운 장치가 6교시부터 AI 의 모든 작업을 통제한다.

## 학습 목표

1. 규칙 없이 일하는 AI 에이전트의 행동을 관찰하고 문제를 짚어 낸다.
2. `AGENTS.md` 를 직접 작성해 에이전트가 따를 규칙을 정한다.
3. `opencode.jsonc` 의 권한 규칙(allow / ask / deny)을 읽고 적용한다.
4. 검증 스크립트와 `pre-commit` 훅으로 "통과해야만 저장된다"를 장치로 만든다.
5. 같은 지시를 다시 내려, 하네스가 있을 때 무엇이 달라지는지 비교한다.

## 1. 개념 — 다섯 요소를 파일로

1교시에 본 다섯 요소를 이번 교시에 하나씩 파일로 세운다.

| 요소 | 세우는 파일 | 종류 | 이번 교시의 단계 |
|---|---|---|---|
| 규칙 | `AGENTS.md` | 부탁 | 2단계 |
| 도구 | `scripts/verify.sh` (+ 2교시의 컨테이너) | — | 4단계 |
| 권한 | `opencode.jsonc` | 잠금장치 | 3단계 |
| 실행 | dev 컨테이너 | 잠금장치 | 2교시에 완료 |
| 검증 | `.githooks/pre-commit` | 잠금장치 | 5단계 |

**부탁과 잠금장치.** `AGENTS.md` 는 AI 가 읽는 글이다. AI 는 대체로 따르지만 반드시 따른다는 보장은 없다. 그래서 정말 일어나면 안 되는 일은 잠금장치로 한 번 더 막는다.

| 일어나면 안 되는 일 | 부탁 (`AGENTS.md`) | 잠금장치 |
|---|---|---|
| AI 가 마음대로 커밋·푸시한다 | "커밋은 사람이 한다" | `opencode.jsonc`: `git commit`, `git push` → deny |
| AI 가 API 키를 읽는다 | ".env 를 읽지 않는다" | `opencode.jsonc`: `.env` 읽기 → deny |
| AI 가 검증 기준을 고친다 | "하네스 파일을 고치지 않는다" | `opencode.jsonc`: `scripts/verify.sh` 고치기 → deny |
| 깨진 코드가 저장된다 | "검증을 통과해야 끝난 것이다" | `pre-commit`: 검증 실패 시 커밋 취소 |
| AI 가 내 PC 의 다른 파일을 건드린다 | — | 컨테이너: `/workspace` 만 보인다 |

## 따라 하기

### 1단계. 실험 — 규칙 없이 시켜 보기 (15분)

먼저 지금 상태가 깨끗한지 확인한다. 실험이 끝나면 이 상태로 되돌린다.

**[dev]**

```bash
git status
```

`nothing to commit, working tree clean` 이어야 한다. 아니라면 4교시 6단계(커밋)를 먼저 한다.

OpenCode 를 연다.

**[dev]**

```bash
opencode
```

아무 조건 없이 한 줄로 시킨다.

**[AI]**

```text
메모 삭제 기능 만들어 줘
```

AI 가 일하는 것을 지켜본다. 끝나면 `/exit` 로 나온다.

**관찰 기록.** 아래 표를 채운다. `git status` 와 `git diff` 로 확인한다.

**[dev]**

```bash
git status
git diff --stat
```

| 관찰할 것 | 결과 |
|---|---|
| 고치기 전에 계획을 말하고 내 승인을 기다렸는가? | |
| 어떤 파일을 고쳤는가? 새로 만든 파일이 있는가? | |
| 없는 번호를 지울 때의 동작을 스스로 정했는가? 어떻게 정했는가? | |
| 성공 상태 코드는 무엇으로 했는가? (요구사항 R5 는 204) | |
| 테스트를 만들었는가? | |
| 검증(`pytest`)을 실행했는가? | |
| 시키지 않은 것을 만들었는가? | |
| 한국어 주석이 있는가? | |
| 명령을 실행하기 전에 물어봤는가? | |

결과는 사람마다 다르다. 옆 사람과 표를 비교한다. **같은 한 줄을 시켰는데 결과가 다르다**는 것 자체가 첫 번째 관찰이다.

AI 가 잘했을 수도 있다. 요즘 모델은 시키지 않아도 테스트를 만들기도 한다. 하지만 "이번에는 잘했다"와 "매번 정해진 대로 한다"는 다르다. 하네스는 뒤쪽을 만드는 일이다.

**되돌리기.** 실험에서 바뀐 것을 모두 버린다.

**[dev]**

```bash
git restore .
git status
```

`git restore .` 는 고쳐진 파일을 마지막 커밋 상태로 되돌린다. `git status` 에 `Untracked files:` (AI 가 새로 만든 파일)가 남아 있으면 그 파일들을 VS Code 에서 지운다. `working tree clean` 이 나올 때까지 한다.

마지막으로 AI 가 스스로 커밋하지 않았는지 본다.

**[dev]**

```bash
git log --oneline -3
```

맨 위가 "4교시: …" 커밋이면 된다. 그 위에 내가 만들지 않은 커밋이 있다면 AI 가 허락 없이 저장한 것이다. 관찰 기록에 적고, 강사와 함께 되돌린다. (이런 일이 3단계에서 권한을 거는 이유다.)

> 방금 한 일을 돌아본다. 커밋해 둔 지점이 있었기 때문에 실험을 마음 놓고 하고 깨끗이 되돌릴 수 있었다. **Git 은 AI 와 일할 때의 안전망**이다.

### 2단계. 규칙 쓰기 — `AGENTS.md` (40분)

OpenCode 는 프로젝트 맨 위 폴더에 `AGENTS.md` 가 있으면 시작할 때 자동으로 읽는다. 지금은 그 파일이 없다.

틀을 맨 위 폴더로 복사한다.

**[dev]**

```bash
cp harness/AGENTS.template.md AGENTS.md
```

VS Code 에서 `AGENTS.md` 를 연다. 괄호 `( … )` 안의 안내 글과 `[작성]` 표시를 지우고, 그 자리에 내 내용을 적는다. 아래 질문을 따라 한 절씩 쓴다. **정답은 없다.** 1단계에서 본 문제를 막으려면 무엇을 적어야 하는지 생각하며 쓴다.

**1절. 프로젝트 소개**

AI 는 이 프로젝트를 처음 본다. 사람 신입에게 설명하듯 적는다.

- 목표: 무엇을 만드는가?
- 사용자: 이 코드를 읽는 사람은 누구인가? → **"프로그래밍을 처음 배우는 학습자"** 라고 적어 두면 AI 가 코드를 쓰는 방식이 달라진다.
- 폴더 구조 표: AI 가 고쳐도 되는 곳과 안 되는 곳을 정한다. `harness/` 와 `scripts/verify.sh` 를 AI 가 고칠 수 있으면 어떤 일이 생길까?

**2절. 도구**

AI 가 "검증하려면 무슨 명령을 쳐야 하지?"를 추측하지 않게 적어 준다. 3·4교시에 내가 직접 쳤던 명령들이다.

- 전체 검증 / 테스트만 / 코드 검사만 / 바뀐 것 보기
- 서버는 어디에서 켜져 있는가? (AI 가 서버를 또 켜려고 하면 포트가 겹친다)

**3절. 권한**

세 칸으로 나눈다. 1단계 관찰 기록의 "명령을 실행하기 전에 물어봤는가?"를 떠올린다.

- 묻지 않고 해도 되는 일 — 자주 하고 위험하지 않은 일
- 먼저 물어봐야 하는 일 — 가끔 필요하지만 사람이 알아야 하는 일
- 하면 안 되는 일 — 되돌리기 어렵거나, 사람의 판단이 필요한 일

**4절. 작업 절차**

1단계에서 AI 는 계획을 말했는가? 이 절에서 **"사람이 진행이라고 할 때까지 파일을 고치지 않는다"** 를 정한다. 검증에 실패하면 몇 번까지 다시 시도하게 할지도 정한다. (무한히 고치게 두면 1교시의 사례 3 이 된다.)

**5절. 코드 규칙**

- 주석: 내가 읽을 수 있어야 한다. 어떤 언어로, 어디에 달게 할 것인가?
- 데이터베이스: 7교시에 배울 내용이라 지금은 `harness/AGENTS.md` 의 해당 부분을 읽고 옮겨 적는다.
- 테스트: **"테스트를 통과시키려고 테스트를 고치지 않는다."** 이 한 줄이 왜 필요한지 옆 사람에게 설명해 본다.

**6절. 검증 — "다 됐다"의 기준**

AI 가 "완료했습니다"라고 말해도 되는 조건을 체크 항목으로 적는다.

**7절. 보고 형식**

틀에 이미 여섯 칸이 있다. 그대로 두거나 고친다.

**다 썼으면 완성본과 비교한다.**

**[dev]**

```bash
diff AGENTS.md harness/AGENTS.md | head -60
```

`<` 로 시작하는 줄이 내 것, `>` 로 시작하는 줄이 완성본이다. 똑같을 필요는 없다. 다음을 점검한다.

- 완성본에 있는데 내 것에 없는 규칙 중 **필요하다고 생각되는 것**을 옮겨 적는다.
- 내 것에만 있는 규칙은 그대로 둔다. 그것이 내 프로젝트의 규칙이다.

시간이 모자라면 완성본을 그대로 가져와도 된다. 단, **처음부터 끝까지 소리 내어 읽고** 가져온다.

**[dev]**

```bash
cp harness/AGENTS.md AGENTS.md
```

### 3단계. 권한 걸기 — `opencode.jsonc` (20분)

지금 맨 위 폴더의 `opencode.jsonc` 에는 모델 이름만 있다. 권한 규칙이 든 완성본으로 바꾼다.

먼저 완성본을 읽는다. VS Code 에서 `harness/opencode.jsonc` 를 연다.

규칙 한 줄은 세 칸이다.

```jsonc
{ "action": "shell", "resource": "git push *", "effect": "deny" }
```

| 칸 | 뜻 | 값 |
|---|---|---|
| `action` | 무엇을 하려는가 | `shell`(명령 실행), `edit`(파일 고치기), `read`(파일 읽기), `webfetch`(웹 페이지 가져오기) … |
| `resource` | 무엇에 대해서인가 | 명령이나 파일 경로. `*` 는 "아무 글자나" |
| `effect` | 어떻게 처리하는가 | `allow`(그냥 허용), `ask`(사람에게 물어봄), `deny`(금지) |

**읽는 순서가 중요하다.** 위에서 아래로 읽으며, 여러 규칙에 걸리면 **가장 아래 규칙이 이긴다.** 그래서 넓은 규칙을 위에, 예외를 아래에 쓴다.

```jsonc
{ "action": "shell", "resource": "*",            "effect": "ask"   },  // 모든 명령은 물어본다
{ "action": "shell", "resource": "pytest *",     "effect": "allow" },  // 단, pytest 는 그냥 허용
{ "action": "shell", "resource": "git commit *", "effect": "deny"  },  // 단, git commit 은 금지
```

**읽기 연습.** `harness/opencode.jsonc` 를 보고 답한다.

1. AI 가 `pip install requests` 를 실행하려 하면? (allow / ask / deny)
2. AI 가 `sh scripts/verify.sh` 를 실행하려 하면?
3. AI 가 `app/main.py` 를 고치려 하면? (힌트: `app/` 을 막는 `edit` 규칙이 있는가? 없다. 이 설정에서 `app/` 은 고쳐도 되는 곳이다. 답은 **허용**이다.)
4. AI 가 `scripts/verify.sh` 를 고치려 하면?
5. AI 가 `.env` 를 읽으려 하면? `.env.example` 은?

**적용한다.**

**[dev]**

```bash
cp harness/opencode.jsonc opencode.jsonc
git diff --stat
```

`opencode.jsonc` 한 파일이 바뀐 것으로 나온다. (`AGENTS.md` 는 새 파일이라 `git status` 에서 보인다.)

**잠금장치 시험.** OpenCode 는 시작할 때 설정을 읽으므로 새로 연다.

**[dev]**

```bash
opencode
```

막아 둔 일을 일부러 시킨다. 하나씩 시키고 무슨 일이 일어나는지 본다.

**[AI]**

```text
.env 파일을 읽고 안에 무슨 변수들이 있는지 알려 줘
```

**[AI]**

```text
git commit -m "test" 명령을 실행해 줘
```

**[AI]**

```text
scripts/verify.sh 의 첫 줄에 주석 한 줄을 추가해 줘
```

**[AI]**

```text
python --version 명령을 실행해 줘
```

| 시킨 일 | 기대하는 결과 | 실제 결과 |
|---|---|---|
| `.env` 읽기 | 막힌다 (deny) | |
| `git commit` 실행 | 막힌다 (deny) | |
| `scripts/verify.sh` 고치기 | 막힌다 (deny) | |
| `python --version` 실행 | 실행 전에 나에게 묻는다 (ask) | |

`ask` 에 걸리면 OpenCode 가 허락을 구하는 선택지를 보여 준다. 화면의 글자는 버전에 따라 조금 다를 수 있다. 의미는 같다. 고를 수 있는 답은 세 가지다.

| 답 | 뜻 |
|---|---|
| once (이번만) | 이번 한 번만 허락한다 |
| always (항상) | 앞으로 같은 종류의 요청은 묻지 않는다 |
| reject (거절) | 허락하지 않는다 |

**always 는 신중하게 누른다.** 누르는 순간 그 명령은 `ask` 에서 `allow` 로 바뀐다. 이 과정에서는 `once` 를 쓴다.

`/exit` 로 나온 뒤 확인한다.

**[dev]**

```bash
git status
git log --oneline -1
```

`scripts/verify.sh` 가 바뀌지 않았고, 새 커밋이 생기지 않았어야 한다. 기대와 다른 결과가 있었다면 그 줄을 `WORKLOG.md` 에 적는다. 권한 규칙의 `resource` 칸 글자 모양이 맞지 않는 경우일 수 있다. (이 저장소의 규칙은 경로 앞에 `*` 를 붙여 두었다.)

### 4단계. 검증 스크립트 읽기 (10분)

`scripts/verify.sh` 를 VS Code 로 연다. 주석과 안내 문구를 빼면 핵심은 네 줄이다.

```sh
set -e
ruff check app tests scripts
pytest -q
echo "검증 통과: 이제 저장(commit)해도 됩니다."
```

- `set -e` — 명령 하나라도 실패하면 **그 자리에서 멈춘다.** 그래서 마지막 줄 "검증 통과"는 앞의 검사가 모두 성공했을 때만 출력된다.
- `ruff check` — 코드를 실행하지 않고 읽어서 실수를 찾는다. 쓰지 않는 import, 정의하지 않은 이름 같은 것들.
- `pytest -q` — 테스트를 실행한다.

ruff 가 무엇을 잡는지 본다. `app/main.py` 맨 아래에 `import os` 한 줄을 추가하고 저장한 뒤 실행한다.

**[dev]**

```bash
sh scripts/verify.sh
```

```text
[1/2] 코드 검사 (ruff) ----------------------------
F401 [*] `os` imported but unused
```

"`os` 를 가져왔지만 쓰지 않았다." 그리고 `[2/2] 자동 테스트` 는 **아예 실행되지 않았다.** `set -e` 때문이다.

`import os` 줄을 지우고 저장한다. `sh scripts/verify.sh` 가 "검증 통과"로 끝나는지 확인한다.

### 5단계. 검증을 통과해야만 저장되게 하기 — `pre-commit` (20분)

지금까지는 `sh scripts/verify.sh` 를 **내가 기억해서** 실행했다. 잊으면 깨진 코드가 저장된다. 이것을 장치로 바꾼다.

Git 에는 "커밋 직전에 이 스크립트를 실행하고, 실패하면 커밋을 취소한다"는 기능이 있다. **훅(hook)** 이라고 한다. `.githooks/pre-commit` 을 VS Code 로 열어 읽는다. 핵심은 이 부분이다.

```sh
sh scripts/verify.sh
result=$?

if [ $result -ne 0 ]; then
    echo "[pre-commit] 검증 실패: 커밋을 취소했습니다."
    exit 1
fi
```

검증을 실행하고, 실패했으면(`0` 이 아니면) `exit 1` 로 끝낸다. 훅이 `0` 이 아닌 값으로 끝나면 Git 은 커밋을 만들지 않는다.

**훅을 켠다.** 이 저장소에서 한 번만 하면 된다.

**[dev]**

```bash
git config core.hooksPath .githooks
git config core.hooksPath
```

둘째 명령이 `.githooks` 를 출력하면 켜진 것이다.

**시험 1 — 깨진 코드를 저장해 본다.**

`app/main.py` 에서 `{"status": "ok"}` 를 `{"status": "okay"}` 로 바꾸고 저장한다. 그리고 커밋을 시도한다.

**[dev]**

```bash
git add app/main.py
git commit -m "실험: 깨진 코드 저장 시도"
```

```text
[pre-commit] 저장하기 전에 검증을 실행합니다...
[1/2] 코드 검사 (ruff) ----------------------------
All checks passed!
[2/2] 자동 테스트 (pytest) ------------------------
(가운데 생략)
>       assert response.json() == {"status": "ok"}  # 답의 내용도 정확히 같아야 한다
E       AssertionError: assert {'status': 'okay'} == {'status': 'ok'}
(가운데 생략)
FAILED tests/test_health.py::test_health - AssertionError: assert {'status': ...

[pre-commit] 검증 실패: 커밋을 취소했습니다.
[pre-commit] 위의 오류를 고친 뒤 다시 커밋하세요.
```

커밋이 만들어졌는지 확인한다.

**[dev]**

```bash
git log --oneline -1
```

맨 위 커밋이 여전히 "4교시: …" 다. **깨진 코드는 저장되지 않았다.**

되돌린다.

**[dev]**

```bash
git restore --staged app/main.py
git restore app/main.py
```

**시험 2 — 정상 코드를 저장한다.** 이번 교시에 만든 하네스 파일들을 커밋한다.

**[dev]**

```bash
git status
git add AGENTS.md opencode.jsonc
git commit -m "5교시: 하네스 세우기 (AGENTS.md, 권한 규칙)"
```

이번에는 검증이 통과하고, 마지막에 커밋이 만들어졌다는 줄(`[main …] 5교시: …`)이 나온다.

> 이제 이 저장소에서는 **사람이든 AI 든 검증을 통과하지 못한 코드를 저장할 수 없다.**
> (참고: `core.hooksPath` 설정은 내 PC 의 `.git/config` 에 저장된다. 저장소를 새로 내려받으면 다시 켜야 한다.)

### 6단계. 실험 — 하네스를 세우고 다시 시켜 보기 (15분)

1단계와 **똑같은 한 줄**을 다시 시킨다.

**[dev]**

```bash
opencode
```

**[AI]**

```text
메모 삭제 기능 만들어 줘
```

이번에는 AI 가 `AGENTS.md` 를 읽고 시작한다. 계획을 말하면 읽어 보고, 이번 실험에서는 구현까지 가지 않는다.

**[AI]**

```text
계획은 잘 봤어. 이번에는 구현하지 않을게. 여기서 멈춰.
```

`/exit` 로 나온다. 1단계의 관찰 기록 옆에 이번 결과를 적어 비교한다.

| 관찰할 것 | 1단계 (규칙 없음) | 6단계 (하네스 있음) |
|---|---|---|
| 고치기 전에 계획을 말하고 승인을 기다렸는가? | | |
| 요구사항 문서(`REQUIREMENTS.md`)를 찾아 읽었는가? | | |
| 상태 코드와 오류 문구를 어디에서 가져왔는가? | | |
| 테스트를 만들겠다고 했는가? | | |
| 명령을 실행하기 전에 물어봤는가? | | |

**[dev]**

```bash
git status
```

바뀐 파일이 있으면 `git restore .` 로 되돌린다.

**그래도 부족한 점.** "메모 삭제 기능 만들어 줘" 한 줄에는 범위도, 하지 말 것도, 완료 조건도 없다. 규칙은 **어떻게 일할지**를 정할 뿐, **이번에 무엇을 할지**는 지시가 정한다. 6교시에 작업 지시서를 쓴다.

---

## 하네스 관점 — 이번 교시에서 세운 것

```text
              AI 가 하려는 일
                    │
          ┌─────────▼──────────┐
 규칙 ──▶ │ AGENTS.md          │  "계획 먼저, 범위 안에서, 검증 후 보고"   (부탁)
          └─────────┬──────────┘
          ┌─────────▼──────────┐
 권한 ──▶ │ opencode.jsonc     │  allow → 통과 / ask → 사람에게 / deny → 차단   (잠금)
          └─────────┬──────────┘
          ┌─────────▼──────────┐
 실행 ──▶ │ dev 컨테이너       │  /workspace 밖은 보이지 않는다   (잠금)
          └─────────┬──────────┘
          ┌─────────▼──────────┐
 검증 ──▶ │ verify.sh          │  ruff + pytest
          │ pre-commit         │  실패하면 커밋 취소   (잠금)
          └─────────┬──────────┘
                    ▼
               Git 에 저장
```

이번 교시에 **코드는 한 줄도 늘지 않았다.** 그런데 프로젝트는 크게 달라졌다. 하네스 엔지니어링은 코드가 아니라 **코드가 만들어지는 환경**을 만드는 일이다.

## 자주 만나는 오류

| 증상 | 원인과 해결 |
|---|---|
| OpenCode 가 `AGENTS.md` 를 읽지 않은 것처럼 행동한다 | 파일이 맨 위 폴더(`/workspace/AGENTS.md`)에 있는지 확인한다. OpenCode 는 시작할 때 읽으므로 `/exit` 로 나갔다가 다시 연다. |
| OpenCode 가 시작할 때 설정 오류를 낸다 | `opencode.jsonc` 를 손으로 고치다 쉼표나 중괄호가 깨졌다. `cp harness/opencode.jsonc opencode.jsonc` 로 다시 가져온다. |
| 3단계에서 막혀야 할 일이 막히지 않는다 | 설정을 바꾼 뒤 OpenCode 를 새로 열지 않았다. 다시 열어도 그대로면 강사에게 알린다. |
| `git commit` 을 했는데 `[pre-commit]` 문구가 나오지 않는다 | 훅이 켜지지 않았다. `git config core.hooksPath` 가 `.githooks` 를 출력하는지 확인한다. |
| 윈도우 PowerShell 에서 커밋하면 훅이 오래 걸리거나 실패한다 | 윈도우에서 커밋하면 훅이 dev 컨테이너에게 검증을 시킨다. 컨테이너가 꺼져 있으면 실패한다. 이 과정에서는 **커밋을 dev 컨테이너 안에서** 한다. |
| `git restore .` 를 했는데 파일이 남아 있다 | 새로 만들어진 파일은 `restore` 로 지워지지 않는다. `git status` 의 `Untracked files:` 에 나온 파일을 직접 지운다. |
| `diff` 결과가 너무 길다 | 정상이다. 틀을 내 말로 채웠으니 줄마다 다르다. 절 제목을 기준으로 끊어서 비교한다. |

## 확인 문제

1. `AGENTS.md` 와 `opencode.jsonc` 는 둘 다 "커밋 금지"를 말한다. 왜 두 군데에 적는가?
2. 권한 규칙에서 `{ "action": "shell", "resource": "*", "effect": "ask" }` 를 맨 **아래**로 옮기면 어떤 일이 생기는가?
3. AI 가 `scripts/verify.sh` 와 `tests/` 를 마음대로 고칠 수 있다면, "검증 통과"라는 말을 믿을 수 있는가? 이유를 쓰시오.
4. `verify.sh` 의 `set -e` 를 지우면 어떤 문제가 생기는가?
5. `pre-commit` 훅이 없을 때와 있을 때, "검증을 통과한 코드만 저장한다"는 약속은 각각 무엇에 의존하는가?
6. 권한 프롬프트에서 `always` 를 누르면 무엇이 바뀌는가? 언제 누르면 안 되는가?
7. 1단계와 6단계의 관찰 기록에서 가장 크게 달라진 항목 하나를 고르고, 그것이 `AGENTS.md` 의 어느 절 덕분인지 쓰시오.
8. 하네스를 세웠는데도 6단계의 지시 "메모 삭제 기능 만들어 줘"가 부족한 이유는 무엇인가?
