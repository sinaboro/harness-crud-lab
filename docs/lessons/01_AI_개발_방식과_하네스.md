# 1교시. AI 개발 방식과 하네스 이해

| | |
|---|---|
| 시간 | 2시간 |
| 실습 결과 | AI·하네스·도구를 구분할 수 있다 |
| 필요한 것 | 웹 브라우저 (아직 아무것도 설치하지 않는다) |

## 수업의 흐름에서 이번 교시의 위치

```text
 ① 요구사항 작성 → ② AI 에게 지시 → ③ 하네스로 제어 → ④ 실행·테스트 → ⑤ 수정·재검증·저장
 └──────────────── 이번 교시: 다섯 단계 전체를 지도처럼 훑어본다 ────────────────┘
```

## 학습 목표

1. AI 모델, AI 에이전트, 하네스, 도구가 각각 무엇인지 한 문장으로 말할 수 있다.
2. 바이브 코딩과 하네스 엔지니어링의 차이를 세 가지 이상 말할 수 있다.
3. 하네스의 다섯 요소(규칙·도구·권한·실행·검증)를 이 저장소의 파일과 짝지을 수 있다.
4. "좋은 요구사항"이 무엇인지 예를 들어 설명할 수 있다.

## 1. 우리가 3일 동안 만들 것

메모장 웹 서비스다. 브라우저에서 메모를 쓰고, 목록으로 보고, 고치고, 지운다.
이 네 가지 동작을 **CRUD**(Create·Read·Update·Delete)라고 부른다. 게시판, 쇼핑몰 장바구니, 할 일 목록 — 대부분의 서비스가 CRUD 로 이루어져 있다.

그런데 이 과정에서 코드를 직접 치는 양은 많지 않다. **대부분의 코드는 AI 에이전트가 쓴다.**
우리가 하는 일은 다음 네 가지다.

1. **무엇을 만들지 정한다.** (요구사항)
2. **AI 가 어떻게 일해야 하는지 정한다.** (하네스)
3. **AI 가 만든 것이 맞는지 확인한다.** (검증)
4. **AI 가 만든 코드를 읽고 이해한다.** (학습)

## 2. 네 가지 낱말 구분하기

### AI 모델

글을 받아서 글을 돌려주는 프로그램이다. 질문을 보내면 답이 온다. 그것이 전부다.
모델은 **내 컴퓨터의 파일을 볼 수 없고, 명령을 실행할 수도 없다.** 대화가 끝나면 아무것도 기억하지 못한다.

> 비유: 전화로만 연결된 아주 똑똑한 상담원. 말은 잘하지만 내 책상 위를 볼 수도, 만질 수도 없다.

### AI 에이전트

AI 모델에게 **손과 눈**을 달아 준 프로그램이다. 에이전트는 모델과 대화하면서 대신 파일을 읽어 주고, 모델이 "이 파일을 이렇게 고쳐"라고 하면 실제로 고치고, "이 명령을 실행해"라고 하면 실행해서 결과를 다시 모델에게 알려 준다. 이 과정을 일이 끝날 때까지 되풀이한다.

> 비유: 상담원(모델)의 지시를 받아 내 책상에서 실제로 일하는 직원.

이 과정에서 쓰는 에이전트는 **OpenCode** 다.

### 도구

에이전트가 일할 때 쓰는 것들이다. 파일 읽기·쓰기, 명령 실행(셸), 테스트 실행기(pytest), 코드 검사기(ruff), 버전 관리(Git), 데이터베이스(PostgreSQL)가 모두 도구다.
도구는 스스로 판단하지 않는다. 시키면 시킨 대로 한다.

### 하네스

에이전트가 **어떤 규칙으로, 어떤 도구를, 어디까지 써서, 어디에서 일하고, 무엇을 통과해야 끝나는지** 정해 둔 장치 전체다.

> 하네스(harness)는 말에게 씌우는 마구(고삐·안장·굴레)다. 말은 힘이 세고 빠르지만, 마구가 없으면 그 힘을 원하는 방향으로 쓸 수 없다. 마구는 말의 힘을 줄이는 것이 아니라 **쓸모 있게 만드는 것**이다.

### 한 장으로 보기

```text
   사람 ──── 요구사항·작업 지시 ───▶  ┌──────── 하네스 ────────┐
                                      │  규칙  권한  검증      │
                                      │    ┌──────────────┐    │
                                      │    │  AI 에이전트 │◀──▶ AI 모델 (OpenRouter 를 거쳐 인터넷 너머에 있다)
                                      │    └──────┬───────┘    │
                                      │           ▼            │
                                      │   도구: 파일·명령·     │
                                      │   pytest·git·DB        │
                                      └────────────────────────┘
   사람 ◀─── 보고·검증 결과 ─────────
```

| 낱말 | 한 문장 | 이 과정에서 |
|---|---|---|
| AI 모델 | 글을 받아 글을 돌려준다 | OpenRouter 로 부르는 모델 |
| AI 에이전트 | 모델의 지시대로 파일을 고치고 명령을 실행한다 | OpenCode |
| 도구 | 에이전트가 일할 때 쓰는 것 | 파일, 셸, pytest, ruff, Git, PostgreSQL |
| 하네스 | 에이전트의 일을 통제하는 장치 전체 | `AGENTS.md`, `opencode.jsonc`, `verify.sh`, `pre-commit`, Docker 컨테이너 |
| OpenRouter | 여러 회사의 모델을 한 주소로 부르게 해 주는 중개 서비스 | API 키 하나로 사용 |

## 3. 바이브 코딩 — 무엇이 문제인가

**바이브 코딩(vibe coding)** 은 AI 에게 말로 시키고, 돌아가는 것 같으면 코드를 읽지 않고 받아들이는 방식이다. 간단한 것을 빨리 만들어 볼 때는 쓸모가 있다. 하지만 이런 일이 생긴다.

**사례 1 — 기준이 없다.**
"메모 앱 만들어 줘"라고 했더니 로그인 화면까지 딸린 앱이 나왔다. 다음 날 같은 말로 다시 시켰더니 전혀 다른 앱이 나왔다. 무엇이 "맞는" 결과인지 정해 둔 적이 없으니 어느 쪽이 맞는지도 알 수 없다.

**사례 2 — 증거가 없다.**
AI 가 "삭제 기능을 추가했습니다. 정상 동작합니다."라고 했다. 며칠 뒤 없는 번호를 지우려 하니 서버가 오류를 내며 멈췄다. AI 는 실행해 보지 않고 "동작한다"고 말한 것이다.

**사례 3 — 되돌릴 수 없다.**
"오류 고쳐 줘"를 다섯 번 반복했다. AI 는 그때마다 여러 파일을 고쳤다. 이제 처음보다 더 망가졌는데, 어느 시점이 멀쩡했는지 알 수 없고 돌아갈 방법도 없다.

**사례 4 — 사고가 난다.**
AI 가 테스트용으로 데이터베이스를 비우는 명령을 실행했다. 거기에는 진짜 데이터가 들어 있었다. 아무도 AI 에게 "거기는 건드리지 마"라고 말한 적이 없다.

**사례 5 — 남는 것이 없다.**
앱은 돌아간다. 그런데 "이 줄이 무슨 뜻이에요?"라는 질문에 답할 수 없다. 고칠 일이 생기면 다시 AI 에게 통째로 맡기는 수밖에 없다.

다섯 사례의 공통점: **AI 가 못해서 생긴 문제가 아니다. 사람이 정해 두지 않아서 생긴 문제다.**

## 4. 하네스 엔지니어링 — 다섯 요소

위의 문제를 하나씩 막는 장치가 하네스의 다섯 요소다.

| 요소 | 질문 | 막아 주는 문제 | 이 저장소의 파일 |
|---|---|---|---|
| **규칙** | 어떻게 일해야 하는가? | 제멋대로 덧붙이기, 계획 없이 고치기 | `AGENTS.md` |
| **도구** | 무엇으로 일하는가? | "제 컴퓨터에서는 되는데요" | `Dockerfile`, `docker-compose.yml`, `scripts/verify.sh` |
| **권한** | 어디까지 해도 되는가? | 위험한 명령, 비밀 값 노출 (사례 4) | `opencode.jsonc` |
| **실행** | 어디에서 실행되는가? | 내 PC 전체를 건드리는 일 | dev 컨테이너 (`/workspace` 만 보인다) |
| **검증** | 다 됐다는 것을 어떻게 아는가? | 확인 없는 "완료" (사례 2) | `tests/`, `scripts/verify.sh`, `.githooks/pre-commit` |

그리고 다섯 요소 앞뒤에 두 가지가 더 있다.

- **요구사항**(앞): 무엇이 맞는 결과인지 정한다. → 사례 1 을 막는다. (`harness/REQUIREMENTS.md`)
- **Git 저장**(뒤): 검증을 통과한 시점마다 저장한다. → 사례 3 을 막는다.

사례 5(남는 것이 없다)는 장치만으로는 막을 수 없다. 그래서 이 과정에서는 **AI 가 쓴 코드를 읽고, 내 말로 설명한 뒤에만 저장한다**는 규칙을 사람에게 건다. (`harness/WORKLOG.md`)

### 규칙과 권한은 어떻게 다른가

- **규칙**은 AI 에게 하는 **부탁**이다. "커밋은 하지 마." AI 는 대체로 지키지만, 잊거나 어길 수 있다.
- **권한**은 **잠금장치**다. `git commit` 을 금지해 두면 AI 가 실행하려 해도 실행되지 않는다.

교실 문에 "들어가지 마시오"라고 써 붙이는 것(규칙)과 문을 잠그는 것(권한)의 차이다. 둘 다 필요하다. 써 붙여야 왜 안 되는지 알고, 잠가야 확실히 막힌다.

## 5. 수업의 흐름 — 다섯 단계

6교시부터는 교시마다 아래 고리를 한 바퀴씩 돈다.

```text
 ① 사람이 요구사항 작성           "무엇을" 만들지 적는다. "어떻게"는 적지 않는다.
        ▼
 ② AI 에이전트에게 개발 지시       작업 지시서를 건넨다. AI 는 먼저 계획을 말한다.
        ▼
 ③ 하네스로 개발 과정 제어         AI 는 규칙과 권한 안에서만 움직인다.
        ▼
 ④ 코드 실행 및 테스트             검증 스크립트를 실행한다.
        ▼
 ⑤ 오류 확인 → AI 수정 → 재검증    실패하면 ④ 로 돌아간다. 통과하면 사람이 읽고 Git 에 저장한다.
```

사람이 하는 일은 ①, 그리고 ②와 ⑤의 **판단**이다. 계획을 승인할지, 결과를 받아들일지는 항상 사람이 정한다.

### 실습 2. 저장소 둘러보기 (20분)

브라우저에서 https://github.com/sinaboro/harness-crud-lab 을 연다. 아직 내려받지 않는다. 읽기만 한다.

1. `harness/AGENTS.md` 를 연다. 3절 "권한"에서 **하면 안 되는 일**을 세 가지 찾아 적는다.
2. `harness/opencode.jsonc` 를 연다. `"effect": "deny"` 가 붙은 줄 중 하나를 골라, 무엇을 막는 규칙인지 말로 풀어 본다.
3. `scripts/verify.sh` 를 연다. 이 스크립트가 실행하는 검사는 몇 가지인가?
4. `app/main.py` 를 연다. 몇 줄인가? 지금 이 서버가 할 수 있는 일은 무엇인가?
5. `checkpoints/lesson11/app/main.py` 를 연다. 3일 뒤의 모습이다. 지금은 읽히지 않아도 된다. 주소가 몇 개인지만 세어 본다.

**확인**: 1번에서 찾은 "하면 안 되는 일"이 2번의 `deny` 규칙으로도 걸려 있는지 짝을 맞춰 본다. 규칙(부탁)과 권한(잠금)이 같은 내용을 두 번 말하고 있다는 것을 확인한다.

### 실습 3. 요구사항 써 보기 (25분)

"메모장을 만들고 싶다"는 말을 요구사항으로 바꿔 본다.

**1단계.** 아무 안내 없이, 메모장이 해야 할 일을 다섯 줄로 적는다. (5분)

**2단계.** 내가 쓴 다섯 줄을 아래 질문으로 점검한다.

- 이 문장을 읽은 두 사람이 **똑같은 것**을 만들까?
- 다 만들었는지 **확인할 방법**이 문장 안에 있는가?
- "메모를 지운다" — 없는 메모를 지우려 하면 어떻게 되어야 하는가? 적었는가?
- "제목을 입력한다" — 제목이 비어 있으면? 1만 자면? 적었는가?
- **만들지 않을 것**을 적었는가?

**3단계.** `harness/REQUIREMENTS.md` 를 열어 R5(메모 지우기)를 읽는다. 내가 쓴 "지우기" 문장과 비교한다.

```text
R5. 메모 지우기 (Delete)
- DELETE /memos/1 을 부르면 상태 코드 204 를 돌려준다. 응답 내용은 없다.
- 지운 뒤 GET /memos/1 을 부르면 404 가 온다.
- 그 번호의 메모가 없으면 404
```

주소나 숫자의 뜻은 4교시에 배운다. 지금 볼 것은 형식이다. **"이렇게 부르면 → 이런 결과가 온다"** 로 적혀 있어서, 읽는 사람마다 다르게 해석할 여지가 없고, 그대로 테스트가 된다.

**4단계.** `REQUIREMENTS.md` 5절 "이번에는 만들지 않는 것"을 읽는다. 왜 이런 목록이 필요한지 옆 사람에게 설명한다.

### 실습 4. 사례에 처방하기 (15분)

3절의 다섯 사례를 다시 읽고, 각 사례를 막으려면 하네스의 어느 요소(또는 요구사항·Git)가 필요한지 적는다. 그 요소를 담당하는 이 저장소의 파일 이름도 함께 적는다.

| 사례 | 필요한 장치 | 담당 파일 |
|---|---|---|
| 1. 시킬 때마다 결과가 다르다 | | |
| 2. 실행해 보지 않고 "동작한다"고 한다 | | |
| 3. 멀쩡하던 때로 돌아갈 수 없다 | | |
| 4. 진짜 데이터를 지웠다 | | |
| 5. 코드를 설명할 수 없다 | | |

## 하네스 관점 — 이번 교시에서 본 것

- 하네스는 AI 를 못 믿어서 만드는 것이 아니다. **믿을 수 있는 결과를 얻으려고** 만드는 것이다.
- AI 가 똑똑해질수록 더 많은 일을 맡기게 되고, 맡기는 일이 커질수록 하네스가 더 중요해진다.
- 이 과정에서 "코딩"이라고 부르는 일의 절반은 **문서를 쓰는 일**이다. 요구사항, 규칙, 작업 지시서, 체크리스트. 이 문서들이 AI 의 결과물을 결정한다.

| "AI 가 다 해 주니 코드를 몰라도 된다" | 읽지 못하면 검토할 수 없고, 검토하지 못하면 맡길 수 없다. 쓰는 양은 줄지만 **읽는 능력**은 더 중요해진다. |
| "하네스는 AI 를 느리게 만든다" | 한 번의 지시는 느려진다. 하지만 되돌리고 다시 시키는 횟수가 줄어 전체는 빨라진다. |
| "프롬프트만 잘 쓰면 된다" | 프롬프트는 규칙(부탁)일 뿐이다. 권한과 검증이라는 잠금장치가 함께 있어야 한다. |
| "테스트가 통과하면 끝이다" | 테스트는 "테스트에 적힌 것"만 확인한다. 테스트 자체를 사람이 읽어야 한다. |
