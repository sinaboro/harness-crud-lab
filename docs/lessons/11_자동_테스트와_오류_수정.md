# 11교시. 자동 테스트와 오류 수정

| | |
|---|---|
| 시간 | 2시간 |
| 실습 결과 | 테스트 통과 (버그를 테스트로 붙잡고, AI 가 고치고, 다시 검증한다) |
| 시작 상태 | 10교시를 마친 상태 (화면까지 완성되어 커밋되어 있다) |

10교시 결과가 없으면 **[dev]** `sh scripts/checkpoint.sh 10` 으로 가져온다.

## 수업의 흐름에서 이번 교시의 위치

```text
 ① 요구사항 작성 → ② AI 에게 지시 → ③ 하네스로 제어 → ④ 실행·테스트 → ⑤ 수정·재검증·저장
                                                                        └─ 이번 교시의 주인공 ─┘
```

지금까지는 "새 기능을 만든다 → 검증한다"였다. 이번에는 순서가 다르다. **이미 있는 버그를 찾는다 → 테스트로 붙잡는다 → AI 가 고친다 → 다시 검증한다.**

## 학습 목표

1. `pytest` 의 실패 출력을 읽고 "무엇을 기대했는데 무엇이 왔는지" 찾는다.
2. 버그를 재현하고, 그 버그를 잡는 테스트를 **수정보다 먼저** 만든다.
3. 실패하는 테스트를 근거로 AI 에게 수정을 지시한다.
4. AI 가 테스트를 고치지 않고 코드를 고쳤는지 확인한다.
5. 요구사항과 테스트의 대응표를 완성한다.

## 1. 개념 — 테스트를 먼저 쓴다 (빨강, 초록)

버그를 고치는 순서가 중요하다.

```text
 나쁜 순서                             좋은 순서
 ─────────────────────────           ─────────────────────────────────────
 1. AI 에게 "고쳐 줘"                  1. 버그를 직접 재현한다
 2. AI 가 "고쳤습니다"                 2. 버그를 잡는 테스트를 쓴다
 3. 눈으로 한 번 확인                  3. 테스트가 실패하는 것을 확인한다   ← 빨강
                                       4. AI 에게 고치게 한다
                                       5. 테스트가 통과하는 것을 확인한다   ← 초록
```

테스트를 먼저 쓰면 세 가지를 얻는다.

- **고쳐졌다는 증거.** 실패하던 테스트가 통과로 바뀐다. "고쳤습니다"라는 말이 아니라 결과다.
- **다시 생기지 않는다는 보장.** 나중에 누가(사람이든 AI 든) 이 버그를 되살리면 테스트가 실패한다.
- **AI 에게 주는 정확한 목표.** "이 테스트가 통과하게 해 줘"는 오해할 수 없는 지시다.

3단계 "빨강 확인"을 건너뛰면 안 된다. 처음부터 통과하는 테스트는 버그를 잡지 못하는 테스트다.

### `pytest` 실패 출력 읽는 법

```text
>       assert response.status_code == 422
E       assert 201 == 422
E        +  where 201 = <Response [201 Created]>.status_code

tests/test_memos.py:120: AssertionError
=========================== short test summary info ===========================
FAILED tests/test_memos.py::test_create_memo_blank_title - assert 201 == 422
```

| 표시 | 뜻 |
|---|---|
| `>` 로 시작하는 줄 | 실패한 확인 |
| `E` 로 시작하는 줄 | 이유. `assert 201 == 422` → **실제로 온 값 == 기대한 값** |
| `tests/test_memos.py:120` | 파일과 줄 번호 |
| `FAILED …::test_create_memo_blank_title` | 실패한 테스트의 이름 |

읽는 순서: **맨 아래 요약부터** 본다. 몇 개가 실패했는지 알고, 위로 올라가 `E` 줄을 읽는다.

### 1단계. 버그 찾기 — 요구사항과 대조 (15분)

`harness/REQUIREMENTS.md` 의 R6 을 다시 읽는다. "*11교시에 추가*"라고 표시된 두 줄이 있다.

- `title` 이 공백뿐(`"   "`)이면 422
- `title` 의 앞뒤 공백은 잘라 내고 저장한다

지금 서버는 이 두 줄을 지키고 있는가? **직접 보낸다.**

**[dev]**

```bash
curl -s -X POST http://app:8000/memos -H "Content-Type: application/json" -d '{"title": "   ", "content": "공백 제목"}'
```

```text
{"id":6,"title":"   ","content":"공백 제목","created_at":"2026-11-10T05:50:36.445321Z","updated_at":"2026-11-10T05:50:36.445321Z"}
```

(`id` 와 시각은 사람마다 다르다.)

**저장되었다.** 요구사항은 422 를 말하는데 201 이 왔다. 버그다.

브라우저에서 http://localhost:8000 을 열어 본다. 제목이 보이지 않는 메모가 목록에 있다. 화면의 제목 칸에 띄어쓰기만 넣고 저장해도 같은 일이 생긴다.

**왜 이런 버그가 있었는가.** 규칙이 "글자가 1자 이상"만 확인하고, 띄어쓰기도 글자 한 자로 센다. 6교시의 테스트도 빈 글자(`""`)만 확인했다. **테스트에 없는 경우는 확인되지 않은 채 남는다.** 테스트 18개가 모두 통과한다는 것은 "버그가 없다"가 아니라 "테스트에 적은 18가지는 맞다"는 뜻이다.

방금 만든 공백 메모는 지운다. `id` 는 위 응답에 나온 번호다.

**[dev]**

```bash
curl -s -X DELETE http://app:8000/memos/6
```

### 2단계. 버그를 테스트로 붙잡기 — 빨강 (20분)

이번 테스트는 **AI 에게 시키지 않고 내가 직접 붙인다.** 무엇이 맞는 동작인지는 사람이 정하는 것이기 때문이다.

먼저 깨끗한 상태인지 확인한다.

**[dev]**

```bash
git status
sh scripts/verify.sh
```

VS Code 에서 `tests/test_memos.py` 를 연다. 파일의 **맨 아래**에 다음 두 테스트를 붙여 넣고 저장한다. 앞의 테스트와 빈 줄 두 개를 띄운다.

```python


def test_create_memo_blank_title(client):
    # 11교시에 추가한 테스트: 공백만 있는 제목은 받지 않는다.
    response = client.post("/memos", json={"title": "   ", "content": "공백 제목"})
    assert response.status_code == 422


def test_title_is_trimmed(client):
    # 11교시에 추가한 테스트: 제목 앞뒤 공백은 잘라서 저장한다.
    response = client.post("/memos", json={"title": "  장보기  ", "content": ""})
    assert response.status_code == 201
    assert response.json()["title"] == "장보기"
```

> 붙여 넣기가 끝나면 두 테스트의 **이름**과 **숫자**만 확인한다. 코드를 이해할 필요는 없다. 각 테스트가 요구사항의 두 줄과 한 줄씩 대응한다는 것만 알면 된다.

실행한다.

**[dev]**

```bash
pytest -q
```

완성 예시 기준의 결과(줄 번호와 개수는 내 파일에 따라 다르다):

```text

________________________ test_create_memo_blank_title _________________________

>       assert response.status_code == 422

FAILED tests/test_memos.py::test_title_is_trimmed - AssertionError: assert ' ...
```

**실패가 정상이다.** 확인할 것:

- [ ] 실패한 테스트가 **방금 추가한 두 개뿐**이다. (`2 failed`)
- [ ] 나머지는 그대로 통과한다. (`18 passed`)
- [ ] 실패 이유가 1단계에서 본 버그와 같다. (`assert 201 == 422`)

만약 방금 추가한 테스트가 **통과**한다면, 버그가 없거나 테스트가 버그를 잡지 못하는 것이다. 테스트를 다시 본다.

**이 상태로 커밋할 수 있을까?** 해 본다.

**[dev]**

```bash
git add tests/test_memos.py
git commit -m "실험: 실패하는 테스트만 커밋"
```

```text
[pre-commit] 저장하기 전에 검증을 실행합니다...
(가운데 생략)

[pre-commit] 검증 실패: 커밋을 취소했습니다.

```

5교시에 세운 장치가 막는다. 버그를 고치기 전에는 저장할 수 없다.

**직접 불러 보기.** 두 가지를 확인한다.

**[dev]**

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://app:8000/memos -H "Content-Type: application/json" -d '{"title": "   ", "content": "공백 제목"}'

```

- 첫 줄: `422` 가 나온다. 1단계에서 `201` 이던 것이다.
- 둘째 줄: 응답의 `title` 이 `"장보기"` 다. 앞뒤 공백이 잘려 저장되었다.

**[dev]**

```bash

```

`422` 가 나와야 한다. `200` 이 나오면 만들기에만 규칙을 넣은 것이다.

브라우저 화면에서도 제목에 띄어쓰기만 넣고 저장해 본다. 저장되지 않고 안내 문구가 나오는가?

## 하네스 관점 — 이번 교시에서 본 것

```text
 버그 발견 ──▶ 테스트 작성(사람) ──▶ 빨강 확인 ──▶ AI 수정 ──▶ 초록 확인 ──▶ 커밋
                    │                   │              │             │
                    │                   │              │             └─ pre-commit 이 통과시킨다
                    │                   │              └─ tests/ 는 건드리지 못한다 (지시서 + git diff 로 확인)
                    │                   └─ 이 상태로는 커밋이 막힌다 (pre-commit)
                    └─ "무엇이 맞는 동작인가"는 사람이 정한다
```

- **기준은 사람이, 구현은 AI 가.** 테스트(기준)를 사람이 쓰고 AI 는 그 기준을 만족시키는 코드만 썼다. 기준과 구현을 같은 쪽이 다 쓰면, 기준을 구현에 맞춰 버릴 수 있다.
- **"테스트 통과"의 뜻을 정확히 안다.** 테스트 18개가 통과하던 때에도 버그는 있었다. 통과는 "적은 것이 맞다"일 뿐이다. 그래서 요구사항과 테스트를 한 문장씩 대조한다.
- **하네스는 자란다.** 버그 하나를 고칠 때마다 테스트가 늘고, 다음에는 같은 버그가 통과할 수 없게 된다.

## 자주 만나는 오류

| 증상 | 원인과 해결 |
|---|---|
| 2단계에서 추가한 테스트가 처음부터 통과한다 | AI 가 앞 교시에서 이미 공백 검사를 넣었을 수 있다. 1단계의 `curl` 을 다시 해 본다. `422` 가 온다면 버그가 없는 것이다. 테스트는 그대로 두고 6단계로 간다. |
| `IndentationError` 또는 테스트가 수집되지 않는다 | 붙여 넣을 때 줄 맞춤이 틀어졌다. `def` 는 줄 맨 앞에서 시작하고, 그 아래 줄은 띄어쓰기 4칸이다. |
| 고친 뒤 다른 테스트가 실패한다 | 수정이 다른 동작을 깨뜨렸다. 테스트가 제 일을 한 것이다. 실패 출력을 AI 에게 붙여 주고, 원인부터 설명하게 한다. |
| AI 가 공백 검사를 `app/main.py` 의 여러 곳에 넣었다 | 지시서 5번 위반이다. 동작은 하지만 규칙이 여러 곳으로 흩어진다. 입력 규칙이 있는 한 곳으로 옮기게 한다. |
| 커밋이 막힌다 | `[pre-commit]` 아래의 출력을 읽는다. 아직 실패하는 테스트가 있다. |
| 화면에서 여전히 공백 제목이 저장되는 것 같다 | Ctrl+F5 로 새로 고친다. Network 탭에서 POST 의 상태 코드가 422 인지 본다. |

3. 2단계에서 추가한 테스트가 처음부터 통과한다면 어떤 두 가지 가능성이 있는가?
4. 테스트 18개가 모두 통과하는데도 공백 제목 버그가 있었던 이유를 설명하시오.
5. 이번 교시에 테스트를 AI 가 아니라 사람이 쓴 이유는 무엇인가?
6. AI 가 테스트를 고쳐서 통과시켰는지 어떤 명령으로, 무엇을 보고 판단하는가?
7. 공백 검사를 만들기 함수와 고치기 함수 각각에 넣는 것과 입력 규칙 한 곳에 넣는 것의 차이를 설명하시오.
